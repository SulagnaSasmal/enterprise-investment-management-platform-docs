Documentation Validation System

The Documentation Validation System is an automated quality gate that runs as a GitHub Actions workflow on every pull request that touches documentation files. It enforces structural, metadata, and content quality standards before changes are merged, preventing documentation debt from accumulating over time.

Quality gate principle: The validation system is not a linter — it is a documentation contract checker. It verifies that documentation meets the commitments made to readers: complete metadata, working links, required sections, and valid code examples.

Validation checks

Metadata validation

  • All required front-matter fields present and non-empty
  • Field values match allowed values (controlled vocabulary)
  • status value is valid lifecycle state
  • category matches known template categories
  • last-reviewed is a valid ISO 8601 date
  • JSON Schema validation via ajv against frontmatter.schema.json

Structure validation

  • Required sections present for the document category
  • No unfilled {{PLACEHOLDER}} tokens remaining
  • No unresolved [REVIEW NEEDED] markers in published documents
  • Heading hierarchy is valid (no skipped levels)
  • Code blocks specify a language identifier
  • Tables have consistent column counts

Link validation

  • All relative internal links resolve to existing files
  • Anchor links (#section) resolve to headings that exist
  • External links checked for HTTP 2xx response (configurable)
  • Image references resolve to files in the assets/ directory

Content quality checks

  • Prose linting via Vale with custom SaaS API style guide rules
  • Passive voice detection (configurable threshold)
  • Consistent API version references within a document
  • Staleness warning if last-reviewed is older than 180 days
  • Minimum word count for key section types (configurable)

GitHub Actions workflow

The validation system ships as a ready-to-use GitHub Actions workflow. Drop it into .github/workflows/docs-validate.yml in your repository.

name: Documentation Validation

on:
  pull_request:
    paths:
      - 'docs/**/*.md'
      - '.repodocs/**'

jobs:
  validate:
    name: Validate documentation
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install RepoDocs AI validator
        run: npm install -g @repodocs-ai/validator

      - name: Validate front-matter schema
        run: repodocs validate schema docs/

      - name: Check for unfilled placeholders
        run: repodocs validate placeholders docs/

      - name: Check internal links
        run: repodocs validate links docs/

      - name: Check required sections
        run: repodocs validate structure docs/

      - name: Run Vale prose linting
        uses: errata-ai/vale-action@reviewdog
        with:
          files: docs/
          config: .repodocs/vale/.vale.ini

Validation CI/CD flow

flowchart TD PR[Pull request opened\nor updated] --> TRIGGER[GitHub Actions triggered\ndocs-validate.yml] TRIGGER --> SCHEMA[Schema check\nfront-matter validation] SCHEMA --> PLACEHOLDER[Placeholder check\nno unfilled tokens] PLACEHOLDER --> LINKS[Link check\ninternal + external] LINKS --> STRUCTURE[Structure check\nrequired sections] STRUCTURE --> VALE[Prose linting\nVale style guide] VALE --> RESULT{All checks\npassed?} RESULT -->|Yes| GREEN[Green check\nPR can be merged] RESULT -->|No| RED[Failed checks\nInline PR annotations] RED --> FIX[Author fixes issues] FIX --> PR

Severity levels

Error
Blocks merge. Required for: missing required metadata, unfilled placeholders in published documents, broken internal links, missing required sections.
Warning
Does not block merge. Flagged for: broken external links, staleness (last-reviewed > 180 days), passive voice above threshold, missing optional metadata.
Info
Informational only. Rendered in the PR summary but not in inline annotations. Examples: word count statistics, readability score, related document suggestions.

Configuration

The validation system is configured via .repodocs/config.yml at the repository root.

validation:
  schema: .repodocs/schema/frontmatter.schema.json
  links:
    check-external: true
    external-timeout-ms: 5000
    ignore-patterns:
      - "localhost"
      - "example.com"
  staleness:
    warn-after-days: 180
    error-after-days: 365
  prose:
    vale-config: .repodocs/vale/.vale.ini
    passive-voice-threshold: 10   # percent
  placeholders:
    error-on-status: [published, review]
    warn-on-status: [draft]

Repository Structure

RepoDocs AI recommends a standard directory layout for documentation in SaaS API repositories. The structure separates documentation source files, templates, AI prompt files, configuration, and generated or published outputs.

Recommended layout

your-repository/
├── docs/                          # All documentation source files
│   ├── api/                       # API reference documentation
│   │   ├── authentication.md
│   │   ├── endpoints/
│   │   │   ├── create-payment.md
│   │   │   └── list-payments.md
│   │   ├── errors.md
│   │   └── webhooks.md
│   ├── guides/                    # Developer guides and tutorials
│   │   ├── getting-started.md
│   │   ├── sdk-integration.md
│   │   └── migration-v1-v2.md
│   ├── architecture/              # Architecture decision records and design docs
│   │   ├── adr/
│   │   │   ├── 001-database-choice.md
│   │   │   └── 002-auth-strategy.md
│   │   └── system-design.md
│   ├── operations/                # Runbooks, playbooks, SLA definitions
│   │   ├── runbooks/
│   │   └── sla.md
│   └── assets/                    # Images, diagrams, downloadable files
│       └── diagrams/
│
├── .repodocs/                     # RepoDocs AI configuration
│   ├── config.yml                 # Validation and tooling configuration
│   ├── schema/
│   │   └── frontmatter.schema.json  # JSON Schema for front-matter validation
│   ├── templates/                 # Local copies of selected templates
│   │   ├── api/
│   │   └── guides/
│   ├── prompts/                   # AI prompt files for this repository
│   │   ├── endpoint-reference.prompt.md
│   │   └── getting-started.prompt.md
│   └── vale/                      # Vale prose linting configuration
│       ├── .vale.ini
│       └── styles/
│
└── .github/
    └── workflows/
        └── docs-validate.yml      # RepoDocs AI validation CI workflow

File naming conventions

Documentation files
kebab-case, lowercase, .md extension. Example: create-payment-intent.md
ADR files
Zero-padded sequence number prefix. Example: 001-database-choice.md
Template files
template. prefix, then type and .md. Example: template.endpoint-reference.md
Prompt files
.prompt.md suffix. Example: endpoint-reference.prompt.md
Asset files
Descriptive kebab-case. Diagrams prefixed with diagram-. Example: diagram-oauth-flow.svg

Git workflow integration

RepoDocs AI documentation changes follow the same Git workflow as code changes:

  • Documentation changes are committed on feature branches, not directly to the default branch
  • Pull requests are opened for all documentation changes, including minor corrections
  • The validation CI workflow runs automatically on every PR touching docs/**
  • At least one reviewer approves documentation changes before merge
  • Documentation and code changes that belong together are committed in the same pull request
  • Changelog entries are updated as part of the same PR as the feature or fix they describe
Co-location pattern: For repositories where documentation drift is a risk, consider co-locating API reference documentation next to the source code it describes. For example, place create-payment.md in the same directory as the controller or handler that implements the endpoint, then symlink or copy it into docs/api/ during the build.
