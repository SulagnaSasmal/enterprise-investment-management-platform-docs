Failover & audit design
Per-event transaction isolation and controlled retries

Design Goals

  • Data integrity: failures do not corrupt positions, cash, or state transitions.
  • Deterministic retries: reprocessing produces consistent outcomes (idempotency).
  • Auditability: every processing decision can be traced end-to-end.
  • Operational control: failover modes are explicit, observable, and reversible.

Event-Level Transaction Isolation

A common pattern is per-event transactional processing: each event (or small event batch) is processed in its own database transaction, allowing partial progress while isolating failures.

sequenceDiagram autonumber participant Q as Event Queue participant W as Worker participant DB as Database participant A as Audit Q->>W: Deliver event E W->>A: Write audit row (E, status=RECEIVED) W->>DB: BEGIN TX W->>DB: Apply business updates for E alt success W->>DB: COMMIT W->>A: Update audit (status=SUCCESS) else failure W->>DB: ROLLBACK W->>A: Update audit (status=FAILED, error_code) W->>Q: Requeue E (retry policy) end

Audit Table (Generic)

The audit model typically captures stable identifiers, processing state, and retry context. Names and exact schemas are intentionally generic. 

EVENT_PROCESSING_AUDIT
  - event_id (stable)
  - event_type
  - portfolio_id (or partition key)
  - business_date
  - status (RECEIVED|IN_PROGRESS|SUCCESS|FAILED|SKIPPED)
  - attempt_count
  - last_error_code
  - last_error_message (sanitized)
  - started_at / finished_at
  - worker_id (logical)

Failover Execution Mode

  • Normal: active workers process events with standard retry policy.
  • Degraded: reduce concurrency to protect dependent systems (DB, downstream services).
  • Recovery: reprocess a targeted partition (e.g., a zone or portfolio group) from a checkpoint.
The “mature” signal here is documenting how retries, isolation, and audit combine to produce operationally safe behavior.
