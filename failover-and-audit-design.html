SunGard Asset Arena Manager

Failover & audit design
JMS retry, JTA transaction isolation, and Oracle audit trail

Design Goals

  • Data integrity: failures never corrupt fund positions, NAV, cash balances, or order state.
  • Deterministic retries: reprocessing a failed event produces the same outcome (idempotency).
  • Auditability: every processing decision is traceable in Oracle audit tables.
  • Operational control: failover modes are explicit, observable via Splunk, and reversible.

Event-Level Transaction Isolation (JTA)

Asset Arena processes trade lifecycle events using per-event JTA transactions managed by WebLogic. Each JMS message is processed in its own database transaction, allowing partial progress while isolating failures to individual events.

sequenceDiagram autonumber participant MQ as IBM MQ Series participant MDB as Message-Driven Bean participant ORA as Oracle RAC participant AUD as Audit Table MQ->>MDB: Deliver JMS message (trade event) MDB->>AUD: Insert audit row (event_id, status=RECEIVED) MDB->>ORA: BEGIN JTA TX MDB->>ORA: Apply business updates (positions, cash, settlement) alt success MDB->>ORA: COMMIT MDB->>AUD: Update audit (status=SUCCESS) MDB->>MQ: Acknowledge message else failure MDB->>ORA: ROLLBACK MDB->>AUD: Update audit (status=FAILED, error_code) MDB->>MQ: Message returned to queue (retry backoff) end

Audit Table Schema

AA_EVENT_PROCESSING_AUDIT
  - event_id          NUMBER(18) -- stable event identifier
  - event_type        VARCHAR2(50) -- TRADE_EXEC, ALLOCATION, SETTLEMENT, CORP_ACTION
  - fund_id           NUMBER(12) -- fund partition key
  - business_date     DATE
  - status            VARCHAR2(20) -- RECEIVED | IN_PROGRESS | SUCCESS | FAILED | SKIPPED
  - attempt_count     NUMBER(3)
  - last_error_code   VARCHAR2(20)
  - last_error_msg    VARCHAR2(500)
  - started_at        TIMESTAMP WITH TIME ZONE
  - finished_at       TIMESTAMP WITH TIME ZONE
  - worker_id         VARCHAR2(50) -- WebLogic managed server name

Failover Execution Modes

  • Normal: all MDB listeners active, standard JMS retry policy (3 retries with exponential backoff).
  • Degraded: reduce MDB pool size to protect Oracle RAC under load; disable non-critical event types.
  • Recovery: replay events for a specific fund or zone from the audit table checkpoint; manual trigger via Asset Arena Admin console.

Dead Letter Queue (DLQ) Handling

  • Events exceeding max retry count are moved to MQ dead letter queue.
  • DLQ monitor raises P1 alert in Splunk with event details.
  • Operations team investigates, fixes root cause, and replays from DLQ or audit checkpoint.
  • All DLQ events must be resolved before the next NAV batch window for the affected zone.
The failover design ensures that a single failed trade event never blocks processing of other events in the same fund or zone. Oracle RAC transparent application failover (TAF) handles database node failures without MDB awareness.
